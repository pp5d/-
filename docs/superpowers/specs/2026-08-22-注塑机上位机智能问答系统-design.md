# 注塑机上位机智能问答系统 · 设计文档

- 日期：2026-08-22
- 状态：已评审（用户逐批确认）
- 范围：面向注塑机上位机领域工程师团队的知识库共建 + 智能问答系统

## 1. 项目背景与目标

### 1.1 背景

使用者是注塑机上位机工程师，日常工作包括：

- 编写注塑机 PLC 运动控制代码（KeStudio/K2 IEC 61131-3）
- 开发 HMI 操作页面
- 对接售后与车间试机人员，协助处理现场问题

随着业务量增长，重复回答同类现场问题（报警处理、功能原理、HMI 使用方法）占用大量时间。需要将"重复答疑"自动化、知识化。

### 1.2 目标

1. 售后/试机人员用自然语言描述问题，系统给出：可能的解决方案、功能原理、功能使用方法，并附参考来源。
2. 工程师团队共建共享知识库：任何人均可提交知识，审核后生效。
3. 未命中知识库的问题自动转人工工单，工程师答复后沉淀为新知识，形成知识飞轮。
4. 领域范围：聚焦"上位机工程师"小领域（注塑机运动控制 + HMI + 相关报警与调试经验）。

### 1.3 成功标准（验收视角）

- 售后人员能通过手机浏览器完成"提问 → 获得带来源的回答"全流程。
- 工程师处理工单后一键沉淀知识，二次提问同类问题能命中。
- 知识从创建到发布全流程可追踪（谁写的、谁审的、什么版本）。
- 内网知识库不出内网；公网只能看到已发布内容。

## 2. 需求确认清单

| 项目 | 决定 |
|---|---|
| 形态 | Web 网页应用（手机浏览器可用） |
| 引擎 | RAG：DeepSeek API（对话生成）+ 本地 BGE-M3（向量化） |
| 部署 | 一套代码两处部署：内网全功能 + 公网只读问答门户，发布同步 |
| 内容 | 问答对、文章、结构化故障案例、代码/表格、附件（图片/视频/PDF） |
| 角色 | 工程师（维护）、售后/试机（提问）、管理员（治理）、全员可提交知识（需审核） |
| 兜底 | 未命中 → 转人工工单 → 答复沉淀为知识 |
| 公网 | 注册账号后使用 |
| 服务器 | IT 部门提供，交付 Docker 部署包 + 安装文档 |
| 大模型 | DeepSeek 开放平台 API（用户已有 Key） |

## 3. 技术选型（方案 A）

- **后端**：FastAPI（Python 3.12）。RAG 管道手写（向量化 + 检索 + prompt 组装），不引入 LangChain 等重型框架，便于控制与排障。
- **前端**：Vue 3 + Element Plus + Vite，中后台组件成熟、移动端自适应。
- **数据库**：PostgreSQL 16 + pgvector 插件（业务数据与向量同库）。
- **向量模型**：BGE-M3（本地部署，sentence-transformers 服务），中英文效果好、免费、数据不出内网。DeepSeek 不提供 embedding API，故单独选型。
- **部署**：Docker Compose 一键编排（前端静态页 + API + PostgreSQL + 向量模型服务 + nginx 反代）。

## 4. 系统架构

### 4.1 整体拓扑（一套代码，两个实例）

```
┌──────────────────────── 公司内网 ────────────────────────┐
│                                                          │
│  工程师电脑 ──┐                                          │
│               ├──► 内网实例（APP_MODE=full 全功能模式）      │
│  管理员电脑 ──┘     · 知识库维护 / 审核 / 发布              │
│                     · 问答（工程师也可问）                  │
│                     · 工单处理                            │
│                     · 管理后台                            │
│                          │                               │
│                          │ ① 发布同步（内网主动推送，       │
│                          │    仅已发布内容，API-Token 认证）│
└──────────────────────────┼───────────────────────────────┘
                           ▼
┌──────────────────────── 公网 ────────────────────────────┐
│                                                          │
│  售后/试机人员（手机/电脑）──► 公网实例（APP_MODE=public）     │
│       · 注册/登录 · 提问（RAG 问答） · 浏览已发布知识         │
│       · 提交知识贡献（进审核队列） · 工单跟踪               │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

要点：

- 同一份代码库，`APP_MODE=full|public` 环境变量切换模式；公网实例后端接口层面禁用知识库写操作与管理接口（前端也不渲染对应页面，双保险）。
- 发布同步由内网主动推送；公网实例物理上不具备写知识库能力。
- **用户体系各自独立**：公网用户自行注册（角色固定为 `support`）；内网用户由管理员创建（`engineer`/`admin`）。同步只同步知识内容与附件，不同步用户数据。
- **公网"提交知识贡献"的边界**：公网实例仅允许创建贡献草稿（进入审核队列，状态 `draft`，无编辑权）；修改/删除/发布正式知识的能力仅存在于内网实例。审核在内网完成，通过后由内网发布。

### 4.2 后端模块划分（FastAPI）

| 模块 | 职责 |
|---|---|
| `auth` | 注册/登录（JWT）、角色权限（engineer/support/admin） |
| `knowledge` | 五类内容 CRUD、状态机（草稿→待审核→已发布/已归档）、版本历史、标签分类、问法别名 |
| `retrieval` | 问题向量化 → pgvector 相似度检索 + 关键词加权 → 混合排序 |
| `llm` | 调用 DeepSeek Chat API，组装"仅基于检索结果"的生成 prompt，流式输出 |
| `ticket` | 未命中兜底：生成工单 → 通知工程师 → 答复 → 一键沉淀为知识 |
| `sync` | 内网→公网增量发布同步（含附件），冲突处理、失败重试 |
| `file` | 附件上传/下载（图片/视频/PDF），类型与大小限制 |
| `admin` | 用户管理、分类标签管理、统计报表（高频问题 Top、知识利用率、工单响应时长） |

### 4.3 前端页面清单

**公网模式（售后/试机，手机优先）**

| 页面 | 说明 |
|---|---|
| 登录 / 注册 | 手机号 + 密码 |
| 问答对话页（核心） | 聊天式：输入问题 → 流式回答 → 附"参考来源"→ 有用/无用反馈 |
| 知识浏览 | 按分类/机型浏览已发布知识，支持搜索 |
| 知识详情 | 正文（代码块、表格、图片），视频播放 |
| 我的工单 | 工单列表、状态跟踪、查看答复 |
| 个人中心 | 提问历史、提交的知识贡献及审核状态 |

**内网模式（工程师/管理员，桌面优先）额外页面**

| 页面 | 说明 |
|---|---|
| 知识库管理 | 列表筛选；编辑器：Markdown 正文、问法别名管理、附件上传、适用机型 |
| 审核中心 | 待审核队列、审核/退回（附意见） |
| 工单处理台 | 工单列表、处理、填写答复、一键沉淀为知识 |
| 管理后台 | 用户管理、分类标签管理、发布同步状态与重试、统计报表 |

## 5. 数据模型（PostgreSQL 核心表）

### 5.1 users（用户）

- 用户名、密码（bcrypt 哈希）、手机号、角色（`engineer`/`support`/`admin`）、所属分组、状态（启用/禁用）、创建时间

### 5.2 knowledge_items（知识主表，五类内容统一存储）

| 字段 | 说明 |
|---|---|
| title | 标题 |
| kind | 类型：`qa`（问答对）/ `article`（文章）/ `case`（故障案例）/ `code`（代码表格） |
| body | Markdown 正文（代码块、表格原生支持） |
| aliases | 问法别名（JSON 数组）：同一知识挂多个"用户可能的问法"，与正文一起向量化，提高口语化提问命中率 |
| case_fields | 结构化故障案例字段（JSON，仅 kind=case）：故障现象、适用机型、排查步骤、解决方案、注意事项 |
| status | `draft` / `pending` / `published` / `archived` |
| author_id / reviewer_id / review_comment | 作者、审核人、审核意见 |
| tags / category / machines | 标签、分类、适用机型 |
| version | 版本号（每次修改 +1） |
| publish_to_public | 是否同步到公网（仅 published 且勾选才同步） |
| stats | 浏览量、被引用次数、有用/无用反馈数 |
| created_at / updated_at | 时间戳 |

### 5.3 attachments（附件）

- 归属知识条目、类型（图片/视频/PDF）、大小限制（图片 ≤10MB、视频 ≤100MB、PDF ≤50MB）、存储路径（Docker 卷）

### 5.4 tickets（工单）

- 提问用户、问题原文、系统检索摘要（记录未命中原因）、状态（open → assigned → answered → closed）、指派工程师、答复内容、沉淀关联（答复转成的知识条目 id）、创建/关闭时间

### 5.5 sync_logs（同步日志，内网维护）

- 知识条目、目标版本、推送状态（pending/success/failed）、错误信息、重试次数、时间戳

### 5.6 知识片段向量表（chunks）

- 知识条目按段落/代码块分块后向量化存储，关联 item_id 与 chunk 顺序；问法别名作为独立 chunk 一并向量化。
- **向量存储方案（2026-08-22 修订）**：原设计用 pgvector 扩展，但开发环境无法访问 GitHub（pgvector Windows 预编译下载源），且注塑机知识库规模（几百~几千条）不需要 ANN 索引。改为 **PostgreSQL JSON 列存向量（1024 维浮点数组），Python 端计算余弦相似度**。未来若知识量增长到需要 ANN 索引，再迁移 pgvector（向量数据不变，仅存储层替换）。

## 6. 核心流程

### 6.1 问答流程（RAG 管道）

```
售后提问"E012 报警怎么处理"
  → ① 向量化问题（本地 BGE-M3）
  → ② 在已发布知识库检索 Top 5 相关片段（pgvector 相似度 + 关键词加权）
  → ③ 相似度 < 阈值？ ──是──► 生成工单转工程师（带原问题和检索摘要）
  →                └─否──► 组装 prompt：检索片段 + 问题 → DeepSeek 流式生成
  → ④ 回答附"参考来源"（知识标题/链接），用户可点赞/点踩
```

- 检索范围：公网实例只检索已发布且 publish_to_public 的知识；内网实例检索全部已发布知识。
- 公网用户的贡献草稿会随同步队列一并推送至内网审核队列（贡献是"从公网流向内网"，与知识发布"从内网流向公网"方向相反，两者各自独立）。
- 生成约束：prompt 明确"仅基于提供的知识片段回答，知识中没有的明确说明不知道"。

### 6.2 知识生命周期（飞轮核心）

```
任何人创建/编辑（draft）
  → 提交审核（pending）
  → 工程师/管理员审核：内容准确性、机型适用范围、格式（通过/退回附意见）
  → 通过 → published（内网立即可检索）
  → 勾选 publish_to_public → 进入同步队列 → 推送到公网
  → 退回 → 作者修改后重新提交
```

### 6.3 工单闭环（未命中 → 新知识）

```
提问未命中 → 自动建工单 → 通知工程师（站内消息）
  → 工程师现场/电话支持 → 系统填写答复
  → 用户收到答复通知
  → 工程师一键"沉淀为知识"：答复自动转成知识草稿，补全问法别名后发布
```

设计意图：每个未命中问题最终都转化为知识库的一部分，系统越用越聪明。

### 6.4 发布同步（内网 → 公网）

- 增量同步：按版本号只推送变更内容，附件一并推送。
- 失败自动重试（指数退避，最多 N 次），sync_logs 可查，管理后台可手动重试。
- 公网实例代码层面禁用知识库写操作。

### 6.5 权限矩阵

| 能力 | support（公网） | engineer（内网） | admin（内网） |
|---|---|---|---|
| 提问 / 看已发布知识 | ✅ | ✅ | ✅ |
| 提交知识贡献 | ✅（需审核） | ✅（需审核） | ✅ |
| 编辑知识 / 审核 | ❌ | ✅ | ✅ |
| 处理工单 | ❌ | ✅ | ✅ |
| 用户管理 / 统计 / 发布控制 | ❌ | ❌ | ✅ |

## 7. 错误处理原则

- LLM 调用失败 → 降级展示检索到的知识原文，并提示"生成服务暂不可用，已为您展示相关资料"。
- 同步失败 → 记录日志、自动重试、管理后台可手动重试。
- 附件超限/类型不符 → 明确中文报错。
- 所有异常返回用户可读的中文提示，不暴露技术堆栈。

## 8. 安全与运维

- 认证：JWT（登录态 7 天）+ bcrypt 密码哈希；管理员可禁用异常账号。
- 公网防线：nginx 反代 + HTTPS（推荐证书）+ 提问接口限流（每分钟 N 次）。
- 同步安全：API-Token 认证 + 公网侧 IP 白名单。
- LLM 安全：DeepSeek API Key 只存服务器环境变量，前端不可见；发送给大模型的仅检索片段 + 问题。
- 备份：备份脚本（pg_dump + 附件目录打包），文档写明 IT 部门定期执行。
- 部署交付：docker-compose.yml 一条命令起全套；部署文档两份（内网版/公网版），含环境变量清单与逐步操作说明。

## 9. 测试策略

- 单元测试（pytest）：知识状态机、权限矩阵、检索排序逻辑、同步增量逻辑。
- 集成测试：问答全流程 API、工单闭环、发布同步。
- 验收走查表：人工验收清单，覆盖核心场景（模拟售后提问未命中 → 转工单 → 工程师答复 → 沉淀知识 → 再次提问命中）。
- 种子数据：内置 10~20 条注塑机领域示例知识（常见报警、模保原理、顶出动作等），部署即可演示联调。

## 10. 实施范围与里程碑

1. **M1 项目骨架**：前后端工程初始化、Docker Compose、数据库迁移、认证与角色权限。
2. **M2 知识库**：五类内容 CRUD、状态机、审核流、附件、问法别名、分类标签。
3. **M3 问答引擎**：BGE-M3 向量服务、分块索引、混合检索、DeepSeek 流式生成、来源引用、反馈。
4. **M4 工单闭环**：未命中建单、工程师处理、沉淀为知识、站内通知。
5. **M5 双区部署**：APP_MODE 切换、发布同步、公网门户只读化、限流与安全加固。
6. **M6 管理后台与统计**：用户管理、同步管理、统计报表、备份脚本、部署文档。
7. **M7 验收**：种子数据、验收走查、缺陷修复、交付。

每阶段完成均可独立验证；M1–M3 完成后内网即可先行试用。
